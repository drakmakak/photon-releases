# Безопасность Photon

Этот документ описывает, что именно защищает Photon "из коробки" — какие
гарантии архитектура даёт по умолчанию, и какие ограничения у неё честно есть
на сегодняшний день.

## 1. Zero-Trust к серверу

Сервер не может прочитать переписку, потому что не хранит того, что для
этого нужно:

- **Username** — только SHA-256 хэш, plaintext-ник никогда не попадает на сервер.
- **Пароли** (обычный, облачный, seed-фраза) — только OPAQUE-конверты (aPAKE),
  сервер не видит и не может подобрать пароль офлайн даже имея полный дамп базы.
- **Содержимое чатов, вложения, реальные ники контактов** — только на
  устройствах, в зашифрованной локальной БД.
- Состав чата на сервере — просто "кто с кем", без имён (только `name_hash`).

## 2. Аутентификация

- **OPAQUE aPAKE** для трёх независимых credential'ов: primary-пароль,
  cloud-пароль, seed-фраза (recovery) — каждый доказывается отдельно,
  компрометация одного не раскрывает остальные.
- **PASETO v4** токены вместо JWT (нет алгоритмической путаницы `alg:none`,
  нет самодельной подписи).
- **mTLS клиентские сертификаты** — у каждого устройства собственный
  TLS-сертификат (Ed25519, подписан внутренним root CA), обычные
  HTTP-запросы вообще не проходят без него. Сессионный сертификат живёт 7
  дней, отдельный renewal-сертификат (90 дней) может только продлить
  сессионный — ничего больше, так что его утечка не эквивалентна утечке
  рабочего сертификата.
- **CRL** (`/.well-known/photon-crl.der`) — отозванные устройства
  проверяются на уровне TLS-рукопожатия в Caddy, до того как запрос вообще
  доходит до приложения.

## 3. Устройства и восстановление сессии

- Новое устройство подтверждается либо QR-пэйрингом (проверка на уже
  доверенном устройстве), либо cloud-паролем.
- **Двухфакторный reissue токенов**: если refresh-токен протух (например,
  после сбоя инфраструктуры), устройство обязано доказать знание пароля
  **и** cloud-пароля — специально сделано двухфакторным, потому что эта
  операция по определению достижима именно с устройства, которое уже
  провалило обычную авторизацию, и однофакторная версия превратила бы
  "выдай новый токен" в оракул для подбора пароля.
- **Quarantine**: 72-часовой grace-период при удалении аккаунта — все
  устройства сразу мгновенно замораживаются (HTTP 423, открытые WebSocket
  рвутся принудительно), отменить можно только тем же двухфакторным
  подтверждением.

## 4. E2E-шифрование сообщений

- **Гибридный handshake**: X25519 (классика) + ML-KEM-1024/Kyber
  (постквантовый) через HKDF — защита остаётся, даже если один из двух
  алгоритмов будет когда-нибудь сломан.
- **Двойной ratchet**, forward-only по обоим направлениям — forward secrecy
  и защита от replay/reorder, плюс явный `rotate()` через свежий ephemeral
  DH для post-compromise security (не просто дошифровка старым ключом — это
  отдельно проверено тестами).
- **Группы через MLS** (RFC 9420, openmls) — sender keys поверх уже
  установленных попарных каналов, не Shamir (Shamir потребовал бы сговора
  участников для расшифровки).
- Сами сообщения — **XChaCha20-Poly1305**.
- Файлы шифруются тем же message-key ratchet'а: `{filename, data}` целиком,
  сервер видит только размер шифртекста, TTL блобов — 7 дней.

## 5. Локальное хранилище (2-of-3 Capsule)

- Мастер-ключ капсулы расщеплён по Shamir на 3 доли: **device_shard**
  (заворачивается под пароль и под Quick-код), **hardware_shard** (в
  Keychain/Keystore), **server_shard** (только для сценария "оба локальных
  осколка потеряны").
- Разблокировка требует любые 2 из 3 — потеря одного канала не блокирует
  вход, но и одного осколка недостаточно для расшифровки.
- **Alarm-код** — блоб неотличимый на диске от обычного Quick-код-врапа; при
  вводе тихо стирает локальные данные без единого подтверждающего диалога
  (антипринуждение).
- Сама БД — зашифрованная SQLite, два независимых слоя ключей (HKDF от
  мастер-ключа).

## 6. Защита от захвата экрана

- **Android**: жёсткий блок через `FLAG_SECURE` — скриншот, запись экрана и
  карточка в Recents рендерятся чёрным, реальный контент физически
  недоступен ОС.
- **iOS/macOS**: у платформы нет API для *предотвращения* скриншота —
  вместо этого детектируется факт скриншота.

## 7. Анти-абьюз на сервере

Rate limiting на каждую чувствительную операцию отдельно (Redis-based):
PQ-handshake, OPAQUE-логин по username, pairing claim, подбор invite-кода
(привязано к сессии, а не к IP — заставляет проходить заново уже
IP-лимитированный handshake), step-up-подтверждения, отправка сообщений и
так далее.

## 8. Честные ограничения

- `hardware_shard` хранится в Keychain/Keystore, это не настоящий Secure
  Enclave/StrongBox hardware-key.
- Disappearing-таймер сообщений — чисто клиентская настройка (сервер и так
  не видит контент, поэтому не может ничего "удалять по таймеру" на своей
  стороне).
- Восстановление через `server_shard` (когда оба локальных осколка
  потеряны) — API есть, но полноценный UI-флоу для этого крайнего случая
  ещё не завершён.
- Mac/iOS не имеют полноценной защиты от скриншота — только детекция
  (ограничение платформы, не архитектуры).
